# Ghostmaxxing visual direction

Version: 2.0.0  
Reviewed: 20 October 2026  
Scope: the software site's design intent and its relationship to current implementation.

## Authority and scope

Ghostmaxxing combines a public poster, an investigative archive and a working browser lab. Keep the political and cultural character while making experiments, evidence and limitations readable.

This guide describes design intent. `styles/tokens.css` supplies exact values; component/page CSS and markup show implementation. `visual-styleguide.html` is a specimen page, not a complete inventory or accessibility certification. `brand-voice.md` governs names, responsibility and claims.

Ghòstati!, in both languages, is NINA's Universal Union initiative. Its workshops and confidential reporting pages belong to Sindacato's visual system. This guide does not prescribe their colours, layout or security instructions. A shared software lab may retain Ghostmaxxing's tool interface.

## Visual grammar

- **Poster:** orange ground, editorial headlines and clear invitations.
- **Archive:** readable surfaces, dates, sources, methods and limitations.
- **Machine:** camera housings, geometric overlays and inspectable test states.
- **Interruption:** pink accents with a meaningful role and a visible boundary.

Preserve the custom mark and camera fleet. Do not replace them with generic cyber-security imagery, tactical HUDs or startup/dashboard decoration. The lab's controls are functional exceptions to the editorial page language.

## Colour, type and surface

Do not duplicate numeric palettes here. Inspect the live swatches in the styleguide and edit `styles/tokens.css` for colour, semantic aliases, type scales and layout tokens.

| Role | Intended treatment |
|---|---|
| Public ground | Orange (`--gm-bg`) |
| Reading surface | Cream, with dark navy body text |
| Structure | Ink borders and headings |
| Machines and dark ground | The named green ramp and soil |
| Live decorative camera iris | Yellow |
| Interruption or consequential accent | Pink, seated on a suitable surface or bounded by ink |

These are roles for the poster/camera system, not a declaration that every runtime status uses the same semantics. In the lab, labels and engine state determine the meaning. A green result is not a safety certificate; colour never replaces text.

Newsreader is the display face, Atkinson Hyperlegible the reading/interface face, JetBrains Mono the compact metadata face. Fonts are self-hosted under `styles/vendor/`. Use the token stacks, including their fallback faces. Do not add external font requests to copy this system.

Prefer flat fields, square editorial panels and visible ink structure. The shared base currently has a flat background. The pink `.gm-site-cta` pill is a deliberate chrome exception. Camera housings, tool controls and specimen widgets have their own geometry; “the only rounded object anywhere” is not an accurate rule. Avoid introducing ornamental shadows or gradients; assess documented component exceptions by function.

## Mark, cameras and SVGs

The mark's two upper live lenses, pink gust and lower spent lens compress the original interruption metaphor. Keep the mark static and recognisable without animation. Use existing painted light/dark and small variants as appropriate; do not invent state-specific copies of the camera fleet.

The fleet has six forms: street pole, wearable glasses, depth sensor array, edge AI cube, dome and bullet camera. Shared class-driven camera drawing and lens-state rules live in `styles/cameras.css`. Page CSS controls placement. Use `data-lens` where the existing component expects it.

Inline class-driven SVG when page CSS must reach its internal parts. Painted SVGs can use `<img>`; host-page `currentColor` does not automatically enter that document. Keep IDs unique for repeated inline instances. Give informative images a meaningful alternative and mark purely decorative repetition accordingly.

“Live”, “reading” and “spent” are drawing states. In a historical context, explain what evidence a state represents. A decorative spent lens is not a measured lab result or proof that a technology family no longer works.

The curved stamp controls in the styleguide are a local specimen. There is no production `lab-js/stamp.js` and the current genealogy does not depend on that demo. Do not add a shared runtime unless a real consumer needs it.

## Current genealogy, not the retired tree

The current `genealogy.html` and `styles/genealogy.css` are generated by `scripts-dev/build-genealogy.py` from `references/REFERENCES.json` and `projects/PROJECTS.json`.

The diagram places dated archive entries against technology-family rows. It generates wide and narrow SVG layouts from the same data; CSS selects the layout. Read the legend and source data for marker types and target categories. A marker records a documented work, not a generic “defeat”. Editorial era spans must not be mistaken for an exhaustive deployment history.

The former centred smoke spine, alternating dossiers, branch composition and pyre narrative are no longer the genealogy layout contract. Existing motifs may still serve the mark or other compositions, but do not restore the old tree when editing the generated page.

Edit datasets or generator, then run `npm run update:genealogy`; do not hand-edit generated HTML or CSS. Check both layouts, long titles, overlapping marks and links to archive entries after regeneration. Do not embed today's item counts in this guide.

## Page patterns and navigation

Content pages generally load `styles/styles.css` and their required page styles. The shared entry imports local fonts, tokens, base and reusable components. The files are in `styles/`, not hypothetical `tokens/`, `components/` or `pages/` subdirectories. Multiple page styles can be necessary; count is not an architectural guarantee.

The shared content header uses the mark/wordmark, Fediverse chip, information menu and reporting destination. It is a common pattern, not byte-identical HTML across generated and hand-authored pages. Update generators/templates as well as outputs. Keep keyboard order and destination clear, and name NINA when inviting confidential contact.

The content footer uses shared chrome and motifs. Tool pages (`lab.html`, `loader.html`, `realtime.html`) have scoped camera-stage chrome and a smaller back link. Do not force the large editorial header into the camera workspace.

- **Home/About:** explain the lab and its limits, then the separate NINA relationship. Do not draw an automatic confidential-report-to-public-feed pipeline.
- **References/projects:** prioritise provenance, demonstration, date, scope and retesting. Preserve distinct source and project meanings.
- **Fediverse/gallery:** explain optional submission, moderation and public distribution. Do not imply implemented inbound automation from a proposed diagram. Public publication is consequential, even on a calm cream surface.
- **Lab:** prioritise the camera, controls, model readiness and textual results; distinguish image similarity from biometric matching.
- **Workshop/report destinations:** provide a clear handoff to NINA. Their editorial assets live in Sindacato; do not restore removed Ghostmaxxing image folders merely to satisfy an old mockup.

## Resilience and review

Core reading and navigation should remain available without decorative scripting. The camera lab itself requires JavaScript, supported APIs and permissions; “every page works as a static poster” cannot describe its functionality.

Keep meaningful states visible with reduced motion, print where relevant, and screenshots. Check keyboard focus on each actual background: `--gm-focus-ring` exists and base CSS uses it, but that alone does not prove contrast on dark surfaces. Test narrow screens, zoom, long translations, informative SVG alternatives and control labels. Colour and position alone must not carry a result.

## Keeping this maintainable

Each document has one job: voice/claims, design intent, or rendered examples. Exact values stay in CSS; chronology stays in datasets; operational status stays beside the implemented feature. Label experimental specimens, not-yet-implemented proposals and historical notes explicitly.

On changes to tokens/components, review the specimen and representative content/tool pages. On generator changes, regenerate outputs. On responsibility or navigation changes, review templates, translations and metadata. Record unresolved checks as bounded tasks with a source and acceptance condition, not permanent “blocking” assertions copied from an old audit.
